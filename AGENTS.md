This is a premium cinematic personal developer portfolio for **Akash S M**.

This is NOT a generic developer portfolio template.

The website must feel like:

* A premium digital product
* A creative technology experience
* A cinematic interactive website
* An engineering portfolio
* A technically sophisticated but usable product

> Design. Develop. Deliver.

# 4. NEXT.JS VERSION RULE

The installed Next.js version is the source of truth.

Before writing or modifying Next.js code:

1. Inspect `package.json`.
2. Confirm the installed Next.js version.
3. Read the relevant documentation under:

`node_modules/next/dist/docs/`

4. Follow the currently installed APIs and conventions.
5. Do not rely on older Next.js knowledge.
6. Pay attention to deprecation notices and breaking changes.

The Next.js agent-rules block generated by Next.js must not be removed or ignored.

Never assume an API exists because it existed in an older Next.js version.

# 8. COMPONENT ARCHITECTURE

Prefer small, reusable, composable components.

Example structure:

```text
src/
├── app/
├── components/
│   ├── layout/
│   ├── navigation/
│   ├── hero/
│   ├── sections/
│   ├── projects/
│   ├── motion/
│   ├── webgl/
│   ├── video/
│   └── ui/
├── data/
├── hooks/
├── lib/
├── utils/
└── styles/
```

Do not create a component for every tiny HTML fragment.

Do not create giant components containing an entire page.

Keep animation logic close to the component that owns it unless it is genuinely reusable.

# 11. ANIMATION PHILOSOPHY

Every animation must have a purpose.

Animation may communicate:

* Hierarchy
* Navigation
* Continuity
* Depth
* Storytelling
* Interaction
* Spatial relationships
* State changes

Do not add animation merely because it is technically possible.

Prefer GPU-friendly properties:

* transform
* opacity
* scale
* rotation
* clip-path where appropriate
* masks where appropriate
* WebGL shader uniforms

Avoid frequent animation of layout-triggering properties such as:

* width
* height
* top
* left
* margin
* padding

unless there is a strong reason.

# 12. GSAP RULES

GSAP and ScrollTrigger are first-class animation tools in this project.

Use them for:

* Scroll-driven storytelling
* Pinning
* Scrubbing
* Horizontal scrolling
* Complex timelines
* Image reveals
* Text reveals
* Section transitions
* Cinematic sequences

Always:

* Scope animations to their component/container.
* Clean up GSAP contexts when components unmount.
* Avoid global selectors when possible.
* Avoid duplicate ScrollTriggers.
* Avoid creating animations repeatedly during React renders.
* Use refs instead of fragile DOM queries where practical.
* Respect responsive breakpoints.
* Test touch scrolling.
* Test reduced-motion behavior.

Prefer GSAP `context()` and appropriate cleanup patterns.

Do not create unnecessary animation timelines.

---

# 13. SCROLLTRIGGER RULES

ScrollTrigger must enhance scrolling, not fight it.

Avoid:

* Excessive scroll hijacking
* Long pinned sections without purpose
* Disorienting scroll behavior
* Animations that prevent users from reaching content
* Horizontal scrolling without a clear reason

Pinned sections should have a clear narrative purpose.

Every scroll-driven section must have a usable fallback.

Test:

* Mouse wheel
* Trackpad
* Touch scrolling
* Mobile browsers
* Reduced motion

---

# 14. SMOOTH SCROLLING

Use Lenis only if it provides a measurable improvement to the experience.

Integrate Lenis carefully with GSAP/ScrollTrigger.

Do not create competing animation loops.

Ensure normal browser scrolling remains functional.

Do not make smooth scrolling so heavy that it causes input lag.

# 15. VIDEO SYSTEM

Video is a major part of the cinematic experience.

AI-generated video assets may be used for:

* Hero backgrounds
* Cinematic transitions
* Project storytelling
* Engineering visualizations
* Brand storytelling
* Section transitions

Video should be **supplementary**, not the only source of important information.

## Video rules

* Never place important textual content only inside video.
* Provide poster images.
* Use `muted`, `playsInline` where appropriate.
* Avoid autoplay with sound.
* Compress production videos.
* Avoid shipping unnecessarily large files.
* Use appropriate formats.
* Lazy-load non-critical videos.
* Do not load every video on initial page load.
* Provide mobile-specific video where necessary.
* Provide static fallbacks.
* Test on slow connections.
* Test on mobile devices.

---

# 16. SCROLL-CONTROLLED VIDEO

Scroll-controlled video may be used for major cinematic sections.

Preferred concept:

```text
Scroll progress
        ↓
ScrollTrigger
        ↓
Normalized progress
        ↓
Video currentTime
```

For example:

```text
0% scroll → beginning of video
50% scroll → middle of video
100% scroll → end of video
```

Use scroll-controlled video selectively.

Do not use it for every section.

Avoid excessive video scrubbing on low-powered mobile devices.

Provide a simplified mobile experience where necessary.

---

# 17. THREE.JS / WEBGL RULES

Three.js and React Three Fiber are enhancement technologies.

They must never be required for understanding important content.

Use WebGL for:

* Atmospheric visuals
* Interactive 3D
* Technical visualization
* Spatial storytelling
* Brand experiences

Do NOT use WebGL simply because the project includes Three.js.

Important text, navigation and project information must remain normal HTML.

Use dynamic imports for heavy WebGL components.

Limit:

* Particle counts
* Geometry complexity
* Texture sizes
* Shader complexity
* Number of WebGL canvases

Avoid multiple simultaneous heavy WebGL scenes.

---

# 18. REDUCED MOTION

Respect:

```css
prefers-reduced-motion
```

When reduced motion is enabled:

* Disable or simplify scroll-driven animation.
* Disable unnecessary parallax.
* Reduce video motion where practical.
* Disable decorative WebGL where appropriate.
* Preserve content and navigation.
* Never make the site unusable.

Reduced-motion users must receive the same information and functionality.

# 27. AI DEVELOPMENT PROTOCOL

Before modifying code:

1. Inspect the existing architecture.
2. Identify affected files.
3. Check package versions.
4. Read relevant official documentation when necessary.
5. Explain the intended implementation briefly.
6. Implement the smallest coherent change.
7. Run validation.
8. Inspect the result.
9. Fix issues caused by the implementation.
10. Report what changed.

Never blindly rewrite working files.

Never replace the architecture to solve a small problem.

Never introduce a dependency without justification.

Never modify unrelated files.

Never remove existing functionality without explicit instruction.

Never assume generated code is correct.

---

# 28. ANIMATION DEVELOPMENT PROTOCOL

For every complex animation:

1. Build the static version first.
2. Confirm layout.
3. Add animation.
4. Test desktop.
5. Test mobile.
6. Test reduced motion.
7. Check performance.
8. Clean up animation lifecycle.
9. Confirm content remains accessible.

Do not implement multiple complex animations simultaneously.

Build and validate one major interaction at a time.

---

# 29. VIDEO DEVELOPMENT PROTOCOL

For every video:

1. Identify why video is necessary.
2. Define the required aspect ratio.
3. Generate/source the master asset.
4. Compress the asset.
5. Create poster image.
6. Create mobile alternative if necessary.
7. Integrate with lazy loading where appropriate.
8. Test slow network conditions.
9. Test mobile.
10. Measure impact on performance.

Never commit unnecessarily large raw video files.
